# HAN-25 — Отчёт исполнения лимитов и перенос остатка между периодами

Linear: [HAN-25](https://linear.app/hangelify/issue/HAN-25) · эпик [HAN-21](https://linear.app/hangelify/issue/HAN-21) ·
модель лимитов [HAN-24](https://linear.app/hangelify/issue/HAN-24) (`2026-11-15-han-24-category-limits-design.md`) ·
фронт [HAN-29](https://linear.app/hangelify/issue/HAN-29)
Дата: 2026-11-17 · Статус: одобрено владельцем 2026-11-17

## Зачем

Пользователь поставил лимиты («Еда — 100 € в месяц») и хочет видеть, уложился ли он:
сколько потрачено, сколько осталось или на сколько превышено — за текущий период и за
прошлые, листая назад. Отчёт читает фронт: экран с вкладками по типу периода и карточка
на дашборде (HAN-29).

Уйти в минус — нормально. Перерасход не пропадает: по умолчанию он уменьшает лимит
следующего периода («долг»), а сэкономленное — увеличивает. Пользователь может решить
иначе: закрыть долг своими деньгами или отказаться от переноса экономии — и сделать это
в том числе задним числом.

**Пример.** Лимит на еду 100 €. В сентябре потрачено 110 € → долг 10 € → лимит на октябрь
90 €. Если пользователь отмечает сентябрь «не переносить» (закрыл из своих денег), лимит на
октябрь снова 100 €. Если в сентябре потрачено 80 €, на октябрь 120 € — или 100 €, если
сентябрь отмечен «не переносить».

## Цели

- `GET /households/:hid/category-limits/report` — исполнение лимитов одного типа за один
  календарный период: по каждой категории с лимитом, итог, прочие траты.
- Перенос остатка (плюс или минус) из периода в следующий, по умолчанию включён; отметка
  «не переносить» на любой прошлый или текущий период и её отмена.
- Факт посчитан так же, как в разбивке трат, и совпадает с ней до цента.
- Пользователь видит, когда цифра неполная (не нашёлся курс).

## Не цели

- Частичный перенос («закрыть 5 € из 10 своими») — либо весь остаток переносится, либо нет.
- Прогноз по темпу, сравнение с прошлыми периодами, уведомления о перерасходе.
- Разбивка «прочих трат» по категориям (только одна сумма).
- «Моя доля» в общем чеке (HAN-33): пока строка чека считается целиком. Когда HAN-33
  появится, факт умножается на долю строки в том же агрегате.
- Список чеков по категории и периоду (клик по категории на фронте — отдельная задача).
- Фронт (кнопки «перенести / не переносить», показ переноса) — HAN-29 или подзадача `[F]`.

## Анти-цели

- Цифра «потрачено» или перенос молча занижены/искажены из-за отсутствующего курса.
- Второй, отличающийся от разбивки трат способ пересчёта валют.
- Перенос, который расходится с фактом после правки старого чека.

## Решения владельца (2026-11-16/17)

1. **Подход к отчёту А** — SQL-агрегат в модуле лимитов, без вызова разбивки трат.
2. **Будущие периоды разрешены.**
3. **Прочие траты** — одно поле `other_spent`.
4. **Курсы** подгружаются модулем курсов на даты чеков (как в разбивке трат); что не
   пересчиталось — в общий список `unconverted`, а у категории — признак неполного факта.
5. `period_type` обязателен; факт по строкам чека; арифметика в центах; лимит без курса —
   в своей валюте с пометкой.
6. **Перенос остатка — в этой задаче.** И долг, и экономия переносятся в следующий период
   автоматически, пока пользователь не отметил период «не переносить»; отметку можно
   поставить задним числом.
7. **Перенос считается при чтении (вариант А переноса)**: хранятся только отметки «не
   переносить», цепочка периодов пересчитывается при каждом отчёте (см. «Подходы»).

## Термины

- **Период** типа T — календарный: `[limitPeriodStart(T, d), limitPeriodEnd(T, d))`
  (`src/common/utils/period-range.ts`).
- **Версия лимита периода** — как в HAN-24: `period_type = T AND effective_from <= start AND
  (effective_to IS NULL OR effective_to > start)`, не больше одной на категорию.
- **Базовый лимит** периода — сумма этой версии, пересчитанная в валюту бюджета.
- **Перенос в период** (`carried_in`) — остаток предыдущего периода цепочки; `> 0` экономия,
  `< 0` долг.
- **Лимит периода** (`limit`) = базовый лимит + `carried_in`.
- **Остаток периода** (`remaining`) = `limit − spent`.
- **Отметка «не переносить»** на период P: остаток P не переходит в следующий период.
- **Цепочка** категории для типа T — подряд идущие периоды типа T, в каждом из которых у
  категории есть версия лимита типа T.

## Перенос

### Правило

Для категории C и периода P типа T:

1. Начало цепочки `P0` — самый поздний из:
   - первый период непрерывной серии периодов типа T, в каждом из которых у C есть версия
     лимита типа T (период без версии типа T рвёт цепочку);
   - период, следующий за последней отметкой «не переносить» до P.
2. `carried_in(P0) = 0`; для каждого следующего `Pk`:
   `carried_in(Pk) = отмечен(Pk−1) ? 0 : remaining(Pk−1)`.
3. Перенос накапливается: `remaining(Pk−1)` уже включает `carried_in(Pk−1)`.

Следствия *(мои решения, приняты владельцем без возражений в обсуждении 2026-11-17)*:

- **Изменение суммы лимита** (новая версия того же типа) цепочку не рвёт — перенос идёт дальше.
- **Смена типа** (месяц ↔ квартал) рвёт цепочку: месячный долг нельзя честно вычесть из
  квартала, начавшегося раньше месяца. Новая цепочка начинается без переноса.
- **Снятый лимит** (`DELETE`) доживает до конца периода; после него версии нет → цепочка
  рвётся; повторно созданный лимит начинает с нуля. `DELETE` (и мягкое удаление категории)
  ставит отметку «не переносить» на текущий период снимаемой версии — иначе лимит,
  созданный заново в следующем же периоде, продолжил бы цепочку без разрыва; отметку можно
  снять через `PUT carry-over`. Установка лимита (`POST`/`PUT`) снимает отметку с текущего
  периода своего типа: `DELETE` и повторный `POST` в одном периоде — период продолжается
  как обычно и переносит остаток дальше (заодно снимается и ручная отметка на этом периоде).
- **Будущие периоды** считаются той же цепочкой: факт будущего периода — по тем чекам, что
  уже есть (обычно 0; чек можно датировать завтрашним днём, `not-after-tomorrow`), перенос
  из текущего периода — по его остатку на сейчас.
- **Правка старого чека** (сумма, дата, категория, удаление, перенос в другой бюджет) сразу
  меняет перенос во все следующие периоды — ничего не хранится, пересчитывать нечего.
- **Мягко удалённая категория** — её лимит доживает до конца периода (HAN-24), отметки
  остаются как есть.

### Неполные данные

- Если в каком-то периоде цепочки до P есть непересчитанные строки категории — перенос в P
  неточный: `carry_incomplete: true`. Непересчитанные строки в перенос не входят.
- Если базовый лимит какого-то периода цепочки нельзя пересчитать (нет курса) — этот
  период рвёт цепочку так же, как период без версии: следующий начинается с нуля,
  `carry_incomplete: true` у всех периодов после него до конца цепочки
  *(моё решение: редкий случай после смены валюты бюджета; честнее показать «неточно», чем
  складывать разные валюты)*.

### Отметки «не переносить»

Таблица `category_limit_carry_stops`:

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | uuid PK | как `BaseEntity` |
| `household_id` | uuid FK → households, `on delete cascade` | для запросов отчёта |
| `category_id` | uuid FK → categories, `on delete cascade` | |
| `period_type` | `limit_period_type` | тип периода, к которому относится отметка |
| `period_start` | `date` | первый день отмеченного периода |
| `created_by_id` | uuid FK → users, `on delete set null`, nullable | кто отметил |
| `created_at` | timestamptz | |

- unique `(category_id, period_type, period_start)`.
- index `(household_id, period_type, category_id, period_start)`.
- `CHECK` в базе на «начало периода» не делаем — проверяет DTO/сервис.
- Миграция `…_AddCategoryLimitCarryStops`; `migration:check` и `migration:drift` чистые.

Отметка на период, который потом оказался вне цепочки (лимит сняли, тип сменили), просто
не влияет на расчёт и не удаляется.

## API

Все эндпоинты — в `CategoryLimitController` (`households/:hid/category-limits`),
`@UseGuards(JwtAuthGuard, HouseholdMemberGuard)`, любой участник бюджета.

### `GET /category-limits/report`

| Параметр | | |
|---|---|---|
| `period_type` | обязателен | `MONTHLY` \| `QUARTERLY` \| `SEMI_ANNUAL` \| `YEARLY` |
| `date` | необязателен | `YYYY-MM-DD`, любой день периода; по умолчанию сегодня (UTC, `todayIsoDate`) |

Ошибки: 400 — неверный тип или дата (`IsCalendarDate`, без нового ограничения диапазона
лет); 403 — не участник. Будущая дата разрешена. Маршрут `report` без параметра не
конфликтует с `PUT/DELETE :categoryId`.

### `PUT /category-limits/:categoryId/carry-over`

Тело: `{ period_type, period_start, carry_over: boolean }`.

- `carry_over: false` — поставить отметку «не переносить» на период (идемпотентно);
  `true` — снять (идемпотентно).
- Ответ 200: `LimitReportCategoryDto` категории за **следующий** период — там видно, как
  изменился лимит *(моё решение: фронту после клика нужен именно новый лимит следующего
  периода; отчёт за отмеченный период он и так держит)*.
- 400: `period_start` не начало периода этого типа; период в будущем (`period_start > today`).
  Текущий период отметить можно.
- 404: категория не в бюджете; у категории нет версии лимита этого типа в этом периоде.
- Мягко удалённая категория — отметку ставить можно, если версия в периоде есть
  *(моё решение: история архивных категорий остаётся управляемой)*.

### Ответ отчёта `LimitReportDto`

```ts
{
  period_type: LimitPeriodType;
  start: string;               // YYYY-MM-DD, первый день периода
  end: string;                 // YYYY-MM-DD, первый день следующего периода (half-open)
  currency: Currency;          // текущая валюта бюджета
  categories: LimitReportCategoryDto[];
  total: {
    base_limit: number;        // сумма базовых лимитов (только пересчитанных)
    carried_in: number;        // сумма переносов
    limit: number;             // base_limit + carried_in
    spent: number;
    remaining: number;         // limit - spent; < 0 = перерасход
    percent: number | null;    // null, если limit <= 0
  };
  other_spent: number;
  unconverted: UnconvertedDto[]; // как в разбивке трат: чеки периода без курса, по валютам
}

LimitReportCategoryDto {
  category_id: string;
  category_name: string;
  category_archived: boolean;
  limit_id: string;            // версия лимита, действующая в периоде
  limit_amount: number;        // в валюте версии
  limit_currency: Currency;    // валюта версии (может отличаться от валюты бюджета)
  base_limit: number | null;   // limit_amount в валюте бюджета; null — нет курса
  carried_in: number;          // перенос из прошлого периода; 0 в начале цепочки
  limit: number | null;        // base_limit + carried_in; null, если base_limit = null
  spent: number;               // в валюте бюджета, только пересчитанные строки
  remaining: number | null;    // limit - spent
  percent: number | null;      // spent / limit * 100, 2 знака; null, если limit null или <= 0
  carry_over: boolean;         // false — период отмечен «не переносить»
  carry_incomplete: boolean;   // перенос посчитан по неполным данным
  unconverted_lines: number;   // строки этой категории за период без курса; > 0 = факт неполный
}
```

- `categories` — по имени категории, затем по id *(моё решение: стабильный порядок;
  «топ перерасходов» фронт сортирует сам)*.
- Категория с лимитом и без трат — в списке с `spent: 0`.
- Архивная категория с действующим лимитом — в списке с `category_archived: true`.
- Нет лимитов этого типа → `categories: []`, нулевой `total` с `percent: null`.
- `percent` может быть > 100 и < 0. При `limit <= 0` (долг съел весь лимит) — `null`;
  фронт показывает перерасход по `remaining`.
- Итог — по категориям с `base_limit !== null`; остальные не входят ни лимитом, ни фактом.
- **`other_spent`** — строки периода без категории и строки категорий, у которых в этом
  периоде нет версии лимита **никакого** типа (пересекающей `[start, end)`). Категория с
  квартальным лимитом в месячном отчёте в `other_spent` не попадает
  *(моя рекомендация, владелец не возразил 2026-11-17)*.

## Расчёт

### Факт

Сумма `bill_sub_categories.amount × fx.factor` по строкам чеков с
`b.household_id = :hid AND b.status = 'confirmed' AND b.deleted_at IS NULL` и `bill_date`
в нужном диапазоне, по `l.category_id` (своя категория строки, HAN-93).

- **По строкам, а не по `bills.amount`**: лимит — на категорию, а у чека несколько
  категорий. Сумма строк может отличаться от итога чека (скидка одной строкой, округления);
  отчёт сходится с разбивкой трат по категориям.
- Отрицательные строки (скидки) уменьшают факт своей категории.
- Черновики, `failed`, дубликаты и удалённые не входят — фильтр по статусу.
- Пересчёт строки — `householdConversionJoin('b')`: курс — последний сохранённый не старше
  7 дней до `bill_date`.
- **Округление — как в разбивке, чтобы совпадать до цента**: `ROUND(SUM(l.amount * fx.factor), 2)`
  по `(category_id, sub_category_id[, период])`, затем сумма округлённых частей.
- Строки с `fx.factor IS NULL` в факт не входят; их число — `unconverted_lines`.

### Курсы

- Перед запросами — `loadRateDays(conn, exchangeRates, hid, chainStart, end)`: модуль курсов
  подгружает до 10 отсутствующих дней из дат иностранных чеков **всей цепочки**. Остальное
  догрузится при следующих открытиях; до тех пор → `unconverted_lines` / `carry_incomplete`.
- Базовый лимит в валюте ≠ валюте бюджета пересчитывается по курсу на
  `min(начало периода, today)` тем же правилом (7 дней, через MDL). Эти дни тоже
  передаются в `ensureDays`.
- Реализация: обобщить фактор из `householdConversionJoin` до фрагмента «фактор из валюты X
  в валюту Y на дату D», использовать для чеков и лимитов. Поведение разбивки трат и
  дашборда не меняется (их int-тесты остаются зелёными).

### Запросы

1. **Версии и отметки** — все версии типа T бюджета с `effective_from < end` и все отметки
   типа T бюджета до `start` включительно (малые таблицы). По ним в TS — категории отчёта,
   начало цепочки каждой и общий `chainStart = min(P0)`.
2. **Траты по периодам** — один агрегат по строкам `bill_date ∈ [chainStart, end)`,
   сгруппированный по `(category_id, sub_category_id, bucket)`, где `bucket` — начало
   периода типа T для `bill_date` (`date_trunc('month'|'quarter'|'year')`, полугодие —
   `make_date(year, CASE WHEN month <= 6 THEN 1 ELSE 7 END, 1)`), с `unconverted_lines`.
   Фильтр по `bills_household_status_date_index`. Тот же запрос (или отдельная часть с
   фильтром по `[start, end)`) даёт данные для `other_spent`.
3. `fetchUnconverted` за `[start, end)` — как у разбивки.
4. Курсы для базовых лимитов цепочки — фактор на каждую дату (можно в запросе 1).

Итого 3–4 запроса на отчёт вместо «одного-двух» из тикета — цена переноса, принятая
владельцем вместе с вариантом А. Проверить `EXPLAIN` на фикстуре и записать в PR.

Глубина цепочки не ограничена: 12 месячных периодов в год на категорию; при росте данных —
ограничить окно (например, 5 лет) отдельной задачей.

### Свёртка

Чистая функция (по образцу `foldSpendingRows`): по категориям проходит цепочку от `P0` до P,
считает `carried_in`, `limit`, `remaining`, `percent`, флаги, итог, `other_spent`; арифметика
в центах (`Math.round(Number(v) * 100)`), `percent = Math.round(spent / limit * 10000) / 100`.
Основная логика переноса проверяется юнит-тестами на ней.

## Тесты

**Юнит** (`limit-report.spec.ts`):
- центы и округление; `percent` > 100, < 0, `null` при `limit <= 0` и `limit: null`;
- перенос долга и экономии; накопление через несколько периодов;
- отметка «не переносить» обнуляет перенос в следующий период и только в него;
- изменение суммы лимита не рвёт цепочку; смена типа и пропуск периода без версии рвут;
- непересчитанный базовый лимит рвёт цепочку и ставит `carry_incomplete`;
- непересчитанные строки в прошлом периоде → `carry_incomplete`;
- итог без категорий с `base_limit: null`; пустой список; сортировка.

**int** (`limit-report.int-spec.ts`):
- границы месяца, квартала, полугодия, года: чек в последний день периода входит, в первый
  день следующего — нет;
- лимит изменён посреди истории: прошлый период берёт старую версию; смена типа месяц →
  квартал (пример из спеки HAN-24);
- пример из «Зачем»: долг 10 € → лимит октября 90 €; отметка сентября → 100 €; снятие
  отметки → снова 90 €; экономия 20 € → 120 €;
- правка суммы старого чека меняет перенос в текущий период;
- снятый лимит виден до конца текущего периода; повторно созданный начинает без переноса;
- `spent` категории совпадает с разбивкой трат за тот же диапазон до цента;
- валюты: пересчёт по курсу на дату чека; без курса и без валюты → `unconverted`,
  `unconverted_lines`; лимит в другой валюте пересчитан, без курса → `base_limit: null`;
- черновики, `failed`, дубликаты, удалённые не считаются; отрицательная строка уменьшает факт;
- строка с категорией без подкатегории считается в своей категории;
- `other_spent`: без категории и категории без лимитов; категория с лимитом другого типа не входит;
- архивная категория с действующим лимитом в отчёте;
- будущий период: перенос из текущего, `spent` по существующим чекам;
- `PUT carry-over`: ставит и снимает отметку идемпотентно; не начало периода → 400; будущий
  период → 400; нет версии в периоде / чужая категория → 404; не участник → 403;
- другой бюджет не протекает (лимиты, отметки, чеки).

## Подходы (рассмотрены)

**Отчёт:**
1. **SQL-агрегат в модуле лимитов** — *выбран*. Признак неполного факта по категории и
   `other_spent` тем же агрегатом. Минус: конвертацию нужно открыть модулю лимитов.
2. **Вызвать разбивку трат и сопоставить в TS** — лишний агрегат, нет непересчитанного по
   категории, связь с форматом ответа дашборда.
3. **Хранимый факт по лимитам** — лишняя сложность.

**Перенос:**
1. **Считать при чтении, хранить только отметки** — *выбран*. Всегда согласовано с чеками,
   решение задним числом работает само, нет фоновых задач. Минус: отчёт читает историю
   цепочки, а не один период.
2. **Хранить перенос по каждому периоду** — нужно обновлять из десятка мест (правка,
   удаление, перенос чека, лимит, курсы); пропуск = молча разъехавшиеся цифры.
3. **Фиксировать при закрытии периода** — правка старого чека не влияет на следующие
   периоды, нужен планировщик.
