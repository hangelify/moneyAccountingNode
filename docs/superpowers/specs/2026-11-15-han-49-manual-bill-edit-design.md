# HAN-49 — источник траты в списке и правка ручной траты

Linear: [HAN-49](https://linear.app/hangelify/issue/HAN-49) · эпик HAN-46 · фронт HAN-51 зависит от этой задачи.
Размер: небольшое изменение.

## Зачем

Ручная трата (`source = manual`, HAN-48) — это чек с одной позицией. Фронт (HAN-51) должен выделять такие траты
в списке и править их на месте (сумма, дата, категория, заметка), не открывая полную форму чека. Правка не должна
оставлять расхождение «итог ≠ сумма позиций».

## Что уже есть (на 5887ec5)

- `source` уже отдаётся в `BillResponseDto` / `BillListItemDto` / `BillDetailResponseDto` (HAN-65).
- `PUT /households/:hid/bills/:id` — частичное обновление; `items` заменяет позиции целиком, позиция принимает
  `category_id` без подкатегории (HAN-95). Сервер не проверяет, что итог равен сумме позиций, а лишь ставит флаг
  `amount_mismatch`.
- Заметка ручной траты хранится в `raw_name` позиции, а не в `bills.description`.
- Удаление — существующее мягкое `DELETE`, менять не нужно.

## Цели / не цели

**Цели:** фильтр по источнику в списке; правка ручной траты без расхождения сумм; короткая правка категории
без отправки `items`.
**Не цели:** короткая правка для `photo` / `bank` (банковские траты получат её в HAN-45, если понадобится);
изменения фронта; смена `source` при правке.
**Анти-цели:** сломать текущее поведение `PUT` для фото-чеков.

## Подходы

- **A. Сервер синхронизирует сам (выбран владельцем).** Для ручной траты с одной позицией `total_amount` переносится
  в позицию; категорию, подкатегорию и заметку можно прислать на верхнем уровне без `items`.
- B. Клиент всегда шлёт итог и позиции, сервер проверяет равенство. Отвергнут: фронт обязан всегда слать `items`.
- C. Отдельный эндпоинт `PUT /bills/:id/manual`. Отвергнут: второй путь записи чека.

**Несколько позиций у ручной траты — разрешены (решение владельца, вариант 2).** Через `items` ручную трату можно
превратить в многопозиционный чек; `source` остаётся `manual`. Короткая правка работает, только пока позиция одна.

## Дизайн

### 1. Фильтр `source`

`ListBillsQueryDto.source?: BillSource[]`, тот же разбор, что у `market_names`: `?source=manual` или
`?source=manual&source=bank`. В `listBills` добавляется условие `b.source = ANY(?)`. Неизвестное значение — 400.

### 2. Короткие поля позиции в `UpdateBillDto`

Новые необязательные поля верхнего уровня:

- `category_id?: string`
- `sub_category_id?: string | null` (`null` — убрать подкатегорию)
- `note?: string` — пишется в `raw_name` позиции (та же длина, что у `raw_name`)

Правила:

- Действуют только у чека с `source = manual` и ровно одной позицией, и только без `items` в том же запросе.
  Иначе — 400 с понятным сообщением.
- Пришёл `sub_category_id` — категория берётся из подкатегории; если вместе с ним пришёл другой `category_id` — 400
  (как сейчас в `findLineCategories`).
- Пришёл только `category_id` — текущая подкатегория сохраняется, если она из этой категории, иначе сбрасывается.
- Чужая / удалённая категория или подкатегория — 400 (существующие `findCategories` / `findSubCategories`).
- При смене категории/подкатегории `category_confidence` и `category_reasoning` обнуляются (как в `applyItems`).

### 3. Синхронизация суммы у `manual`

- Без `items`, одна позиция: `total_amount` записывается и в чек, и в позицию; `price_per_unit` обнуляется.
- Без `items`, позиций больше одной: `total_amount` меняет только чек; если после этого итог не сходится
  с суммой позиций (с допуском `BILL_ITEM_TOLERANCE`) — 400.
- С `items` и с `total_amount`: если итог не сходится с суммой `items` — 400.
- С `items` без `total_amount`: итог чека = сумма `items`, **только если сумма позиций изменилась** (по итогам ревью: перекатегоризация строк старой траты с уже расходящимся итогом не меняет потраченную сумму).

Итог: у ручной траты после любого успешного `PUT` `amount_mismatch = false`. Для `photo` / `bank` поведение `PUT`
не меняется (короткие поля для них — 400).

### 4. Тесты

- int: `source=manual` возвращает только ручные; несколько значений; неверное значение — 400.
- int: правка суммы ручной траты меняет сумму позиции, `amount_mismatch = false`.
- int: правка категории без подкатегории: подкатегория из другой категории сбрасывается, из той же — остаётся;
  `sub_category_id: null` убирает её; подкатегория чужой категории вместе с `category_id` — 400.
- int: `note` меняет `raw_name`.
- int: короткие поля у фото-чека / вместе с `items` / у многопозиционной ручной траты — 400.
- int: ручная трата превращается в многопозиционную через `items`; несходящийся итог — 400; без `total_amount`
  итог пересчитывается.
- unit: валидация новых полей DTO.

## Решения исполнителя (можно оспорить)

- `source` в фильтре — массив, а не одно значение (фронтовому фильтру HAN-51 может понадобиться «ручные + банк»).
- `note` добавлен в короткие поля: в карточке HAN-51 заметку тоже правят на месте.
- Короткие поля — только для `manual`; обобщение на `bank` оставлено HAN-45.
- Несходящийся итог у ручной траты — 400, а не молчаливая подгонка.
